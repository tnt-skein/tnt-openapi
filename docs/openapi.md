# Описание API

Описание API, которое пишут рядом с кодом руками, расходится с ним молча.
Маршрут появился и не описан — чужой клиент узнает о нём, когда
сломается. Поле переименовали в форме и забыли в документе — клиент
шлёт старое имя, а проверка его отвергает. Сверка документа с кодом
ловит часть таких расхождений, но работу не снимает: документ всё равно
пишется вторым текстом.

Пакет `tnt-openapi` собирает документ OpenAPI 3.0 из того, что уже
объявлено в коде. Пути, способы и параметры пути даёт роутер
[`tnt-router`](https://github.com/tnt-skein/tnt-router) — ограничение
шаблона становится схемой параметра. Схемы тел и ответов дают формы
[`tnt-data`](https://github.com/tnt-skein/tnt-data), те же, что проверяют
вход и собирают выдачу. Параметры строки запроса даёт объявленный запрос
[`tnt-query`](https://github.com/tnt-skein/tnt-query) с его белым
списком. Руками пишутся только слова — что делает операция и что значит
её ответ, — и описание операции ищется по имени маршрута.

Документ собирается только целиком согласным с роутером. Маршрут API без
описания, описание без маршрута, слово о параметре, которого нет в пути,
две операции на одном пути — отказ парой `nil, problems` со всеми
расхождениями сразу. Документ, в котором часть маршрутов молча пропала,
выглядит полным и врёт клиенту.

Документ, написанный руками, пакет сверяет с маршрутами тоже
(`openapi.served`): по способу и пути целиком, от начала сервера.

Зависит от `tnt-router` (разбор шаблона), `tnt-data` (формы и их схемы)
и [`tnt-must`](https://github.com/tnt-skein/tnt-must) (проверки
объявления). `tnt-query` пакету не нужен: запрос приходит в описание
операции аргументом, и пакет зовёт у него только `parameters()`.
Настроек и состояния нет — ни `configure`, ни `new`, ни `default`,
ни `status`: описание — значение, собранное объявлением.

## Как пользоваться

```lua
local data = require('tnt.data')
local openapi = require('tnt.openapi')
local query = require('tnt.query')
local router = require('tnt.router')

local Customer = data.define({
    name = 'Customer',
    about = 'Клиент',
    fields = {
        { 'id', 'integer', min = 1 },
        { 'name', 'string', min = 1, max = 64, about = 'Имя, как его видят в панели' },
    },
})

local NewCustomer = data.define({
    name = 'NewCustomer',
    fields = { { 'name', 'string', min = 1, max = 64 } },
})

local Problem = data.define({
    name = 'Problem',
    about = 'Отказ по RFC 9457',
    fields = {
        { 'title', 'string' },
        { 'status', 'integer' },
        { 'detail', 'string', optional = true },
    },
})

local Customers = query.define({ shape = Customer, filters = { 'name' }, sorts = { 'name' } })

local web = router.new()

web.group('/api/v1', { name = 'customers.' }, function(r)
    r.get('/customers', list, { name = 'list' })
    r.get('/customers/:id<int>', show, { name = 'show' })
    r.post('/customers', create, { name = 'create' })
end)

local Api = openapi.define({
    title = 'Магазин',
    version = '1',
    servers = { { url = '/api/v1' } },
    refusal = { schema = Problem, media = 'application/problem+json' },
    operations = {
        ['customers.list'] = {
            summary = 'Клиенты',
            query = Customers,
            responses = {
                [200] = { description = 'Клиенты', schema = Customers.schema(Customer) },
            },
        },
        ['customers.show'] = {
            summary = 'Клиент по номеру',
            params = { id = 'Номер клиента' },
            responses = { [200] = Customer, [404] = 'Клиента нет' },
        },
        ['customers.create'] = {
            summary = 'Завести клиента',
            body = NewCustomer,
            responses = { [201] = Customer, [422] = 'Поля не прошли проверку' },
        },
    },
})

local document = assert(Api.document(web))

web.get('/openapi.json', function()
    return router.json(document)
end)
```

Документ — обычная таблица: её отдают ответом JSON, пишут в файл
`yaml.encode` или сверяют с файлом в проверках. Операция клиента по номеру
в нём выглядит так:

```lua
print(yaml.encode(document.paths['/customers/{id}']))
```

```yaml
get:
  operationId: customers.show
  summary: Клиент по номеру
  parameters:
  - name: id
    in: path
    required: true
    description: Номер клиента
    schema:
      type: integer
  responses:
    '200':
      description: Клиент
      content:
        application/json:
          schema:
            $ref: '#/components/schemas/Customer'
    '404':
      description: Клиента нет
      content:
        application/problem+json:
          schema:
            $ref: '#/components/schemas/Problem'
    default:
      description: Отказ, не названный у операции
      content:
        application/problem+json:
          schema:
            $ref: '#/components/schemas/Problem'
```

Порядок ключей в выводе `yaml.encode` свой: встроенный YAML ключей
не сортирует. Здесь он переставлен для чтения.

Путь начинается от сервера описания: `/api/v1` ушло в `servers`, а в
`paths` лежат `/customers` и `/customers/{id}`. Параметр `id` — целое:
ограничение `<int>` шаблона стало схемой. Отказ `404`, описанный одним
словом, получил тело отказа описания, а `default` дописан сам. В
`components.schemas` — `Customer`, `NewCustomer` и `Problem`: все формы,
на которые сослалось описание, и все вложенные в них.

Маршрут, объявленный позже и не описанный, документ не пропускает:

```lua
web.delete('/api/v1/customers/:id<int>', remove, { name = 'customers.remove' })

Api.document(web)
--> nil, { 'Маршрут customers.remove (DELETE /api/v1/customers/:id<int>) не описан.' }
```

### Что есть у пакета

| Имя | Что это |
|---|---|
| `openapi.define(spec)` | объявляет описание; негодное — исключение |
| `Api.document(router)` | документ OpenAPI 3.0 таблицей либо `nil, problems` |
| `Api.title`, `Api.version` | название и версия API из объявления |
| `openapi.served(document, router, opts)` | сверка готового документа с маршрутами: `true` либо `nil, problems` |
| `openapi.VERSION` | версия OpenAPI документа — `3.0.3` |

Роутер — экземпляр `tnt-router` либо что угодно с `routes()`, отдающим
маршруты таблицами `{ method, pattern, name }`.

## Объявление

| Ключ | Что это |
|---|---|
| `title` | название API — `info.title`; обязательно |
| `version` | версия API — `info.version`; обязательно |
| `description` | что это за API — `info.description` |
| `servers` | серверы `{ { url, description } }`; путь первого — начало путей описания |
| `select` | функция маршрута: входит ли он в API; по умолчанию — именованные |
| `refusal` | тело отказа: форма либо `{ schema, media, description }` |
| `security` | требования входа для всего документа, как в OpenAPI |
| `security_schemes` | схемы входа — `components.securitySchemes`, как в OpenAPI |
| `operations` | описания операций по именам маршрутов; обязательно |

Операция:

| Ключ | Что это |
|---|---|
| `summary`, `description` | слова операции |
| `tags` | метки списком строк |
| `deprecated` | `true` — операция уходит |
| `params` | слова параметров пути по именам: `{ id = 'Номер клиента' }` |
| `query` | объявленный запрос `tnt-query`: параметры строки запроса |
| `parameters` | прочие параметры списком, как в OpenAPI: заголовки, куки |
| `body` | тело запроса: форма либо `{ schema, media, description, optional }` |
| `responses` | ответы по кодам; хотя бы один |
| `security` | требования входа операции; `{}` — операция открыта |

Код ответа — целое от 100 до 599, `'default'` либо диапазон `'4XX'`.
Строка `'200'` отвергается: у кода одна запись, и две записи одного
кода в одной таблице затёрли бы друг друга молча. Ответ пишется тремя
способами:

```lua
responses = {
    [200] = Customer,                                        -- форма: слово — about формы, иначе имя
    [404] = 'Клиента нет',                                   -- слово: у отказа — тело отказа описания
    [207] = { description = 'Сделано не всё', schema = Report, media = 'application/json' },
}
```

Тело запроса — форма (`body = NewCustomer`, тело обязательно) либо
таблица: `{ schema = …, media = 'application/merge-patch+json',
description = 'Правка', optional = true }`. Тип содержимого по умолчанию —
`application/json`.

Схема на месте формы — любая схема OpenAPI таблицей. Форма может стоять
в ней где угодно и станет ссылкой: `{ type = 'array', items = Customer }`
в документе — `{ type = 'array', items = { $ref = '#/components/schemas/Customer' } }`.
Параметры `parameters` проходят той же заменой. Остальное в схеме пакет
не проверяет и переносит как есть, вместе с разметкой пустого словаря
`__serialize`: без неё `{}` уехал бы в JSON списком `[]`.

Тело списка описывает сам запрос: `Customers.schema(Customer)` — схема
ответа `respond` с `data`, `meta` и `links` по странице объявления,
а запись в ней — форма, и в документе она та же ссылка на `Customer`
(документ [`tnt-query`](https://github.com/tnt-skein/tnt-query/blob/main/docs/query.md),
«Схема ответа списка»). Схема списка, написанная
руками, — вторая копия выдачи: список начнёт считать всего или листать
курсором, а описание останется прежним.

### Отказ описания

`refusal` — тело отказа приложения, одно на все операции. Его получает
каждый ответ 4xx, 5xx и `default`, описанный без своей схемы: словом либо
таблицей без `schema`. Ответ со своей схемой её и оставляет.

Ответ `default` есть у каждой операции, даже если его не назвали:
упавший обработчик отвечает 500 на любом адресе, и описание без этого
ответа обещало бы, что отказов, кроме названных, не бывает. Его слово —
`description` из `refusal`, иначе «Отказ, не названный у операции»; без
`refusal` у него нет тела.

## Что берётся у роутера

Описание операции ищется по имени маршрута. Имя переживает перенос
группы под другое начало пути, а шаблон — нет; имя роутер держит
единственным сам. Какие маршруты составляют API, решает `select`:
по умолчанию — все именованные, потому что имя — договор с клиентом,
а страницы и раздача файлов открываются ссылкой. Маршрут API без описания
и маршрут, который `select` взял, а имени у него нет, — расхождения.
Описанный маршрут вне `select` в документ входит: выкладка метрик живёт
вне начала API, но описать её можно.

Шаблон разбирает сам роутер. Ограничение участка становится схемой
параметра:

| Ограничение | Схема |
|---|---|
| нет | `{ type = 'string' }` |
| `<int>` | `{ type = 'integer' }` |
| `<uuid>` | `{ type = 'string', format = 'uuid' }` |
| `<alpha>` | `{ type = 'string', pattern = '^[A-Za-z]+$' }` |
| `<slug>` | `{ type = 'string', pattern = '^[A-Za-z0-9_-]+$' }` |

Образцы роутера — образцы Lua, а `pattern` в OpenAPI — регулярное
выражение ECMA, поэтому они записаны заново, по смыслу. Своя проверка
функцией и ограничение группы `where` в шаблон не попадают, и такой
параметр описывается строкой.

Один маршрут бывает несколькими путями. Параметр пути в OpenAPI
обязателен всегда, а необязательный участок в конце — это адрес и с ним,
и без него; хвост `*path` подходит к пустому остатку. Поэтому каждый
такой адрес — свой путь описания, от длинного к короткому:

```lua
web.get('/reports/:year<int>/:month?', report, { name = 'reports' })
web.get('/files/:dir/*path', file, { name = 'files' })

--> /reports/{year}/{month}   operationId = reports
--> /reports/{year}           без operationId
--> /files/{dir}/{path}       operationId = files
--> /files/{dir}              без operationId
```

Опознаватель `operationId` — имя маршрута, и только у самого длинного
пути: в документе он обязан быть единственным. Необязательных участков
перед хвостом роутер не разворачивает — `/files/:dir?/*path` на `/files`
отвечает 404, — и описание их не разворачивает тоже. Хвост — обычный
параметр: клиент, кодирующий косую черту в значении (`a%2Fb`), получает
тот же хвост, что и по `a/b`, потому что роутер раскодирует участки
по одному.

Путь документа считается от пути первого сервера: `/api/v1` в `servers`
и маршрут `/api/v1/customers` дают путь `/customers`, а сам `/api/v1` —
путь `/`. Маршрут вне начала сервера пишется целиком и со своим
сервером — корнем того же узла (`servers = { { url = '/' } }`, у полного
адреса — `https://узел/`): иначе клиент приложил бы к нему начало
сервера и ушёл по адресу, которого нет.

`HEAD` и `OPTIONS`, объявленные своим маршрутом, — свои операции.
`HEAD`, который роутер обслуживает сам за `GET`, в документ не пишется.

## Расхождения

`Api.document` отдаёт `nil, problems` — список всех расхождений сразу,
в порядке маршрутов (у роутера он — по шаблону), затем описания без
маршрута по именам:

```lua
local shop = router.new()

shop.get('/a/:id<int>', show, { name = 'by_number' })
shop.get('/a/:id<uuid>', show, { name = 'by_uuid' })
shop.get('/api/b', show, { name = 'b' })
shop.get('/api/c', show)
shop.any('/hook', show, { name = 'hook' })
shop.get('/items/:id', show, { name = 'item' })

local Drifted = openapi.define({
    title = 'Магазин',
    version = '1',
    select = function(route)
        return route.name ~= nil or route.pattern:find('^/api/') ~= nil
    end,
    operations = {
        by_number = { responses = { [200] = 'Да' } },
        by_uuid = { responses = { [200] = 'Да' } },
        hook = { responses = { [200] = 'Да' } },
        item = { params = { uid = 'Номер' }, responses = { [200] = 'Да' } },
        ghost = { responses = { [200] = 'Да' } },
    },
})

Drifted.document(shop)
--> nil, {
-->     'Маршруты by_number (GET /a/:id<int>) и by_uuid (GET /a/:id<uuid>) дают одну операцию GET /a/{id}.',
-->     'Маршрут b (GET /api/b) не описан.',
-->     'Маршрут GET /api/c без имени: описание ищется по имени.',
-->     'Маршрут hook (ANY /hook) объявлен на любой способ: описанию нужен способ.',
-->     'Описание item: у маршрута нет параметра uid.',
-->     'Описание ghost: маршрута с таким именем нет.',
--> }
```

Без имени маршрут может быть в API только по своему `select`: по
умолчанию безымянный в API не входит. Два шаблона `/a/:id<int>`
и `/a/:id<uuid>` роутер различает ограничением, а OpenAPI — нет: для него
это один путь `/a/{id}`.

Каждый вызов `document` собирает документ заново: правка одного документа
не видна следующему, и таблицы объявления в документ не попадают.

## Сверка документа, написанного руками

```lua
local text = yaml.encode(document)   -- файл описания; здесь — документ, собранный выше

openapi.served(yaml.decode(text), web)
--> nil, { 'Операция DELETE /api/v1/customers/{id} обслуживается, но не описана.' }
```

Документ собран до маршрута удаления, и сверка его называет. Сходится
документ с маршрутами — `served` отдаёт `true`.

`served` сличает операции документа с маршрутами, которые `select`
относит к API (по умолчанию — именованные), по способу и пути целиком:
путь считается от сервера пути, если он у пути есть, иначе от первого
сервера документа, а маршрут разворачивается в пути так же, как у
`document`. Способ, добавленный к уже описанному пути, сверка одних путей
не заметила бы. Расхождения — сначала маршруты на любой способ: сверять
их нечем; затем операции, которые обслуживаются, но не описаны,
в порядке маршрутов; затем описанные, но не обслуживаемые, по порядку
строк «СПОСОБ путь»:

```lua
local site = router.new()

site.post('/api/v1/login', login, { name = 'login' })
site.any('/hook', hook, { name = 'hook' })

openapi.served({
    servers = { { url = '/api/v1' } },
    paths = { ['/ghost'] = { get = { responses = { ['200'] = { description = 'Да' } } } } },
}, site)
--> nil, {
-->     'Маршрут ANY /hook объявлен на любой способ: сверять нечего.',
-->     'Операция POST /api/v1/login обслуживается, но не описана.',
-->     'Операция GET /api/v1/ghost описана, но не обслуживается.',
--> }
```

`HEAD` у пути с `GET` обслуживается — роутер отвечает на него сам тем же
обработчиком, — но описывать его у каждого `GET` не нужно. Слов, тел
и ответов сверка не читает: по маршруту их не видно. Имя параметра —
часть пути: `/customers/{uid}` в документе и `:id` в шаблоне расходятся.

Настройка у сверки одна — `select`: `openapi.served(document, web, {
select = function(route) … end })`. Документ, собранный `document`
с умолчанием `select`, свою сверку проходит всегда; со своим `select`
описанный маршрут вне него сверка назовёт необслуживаемым — пусть
и сверка получит тот же `select`, что взял описанные.

## Отказы объявления

Негодное объявление — исключение со строкой того, кто позвал
`openapi.define`. Текст называет место и значение:

```lua
--> описание API.title — непустая строка, а не nil
--> описание API: ключа «titel» нет, есть description, operations, refusal, security, security_schemes, select, servers, title, version
--> описание API.operations: имя маршрута — непустая строка, а не «»
--> операция «a».params.id — строка, а не число
--> операция «a».query.parameters — функция или вызываемая таблица, а не nil
--> операция «a».responses — хотя бы один ответ, а не пустая таблица
--> операция «a».responses: код ответа — целое от 100 до 599, «default» либо «4XX», а не «200»
--> операция «a».responses[200] — слово, форма либо таблица ответа, а не 5
--> операция «a».responses[200]: тип содержимого без схемы — описывать нечего
--> две разные формы зовутся Address
```

Операции проверяются по порядку имён, ответы — по порядку кодов:
из двух негодных называется всегда одна и та же. Две разные формы
под одним именем видны только на всём списке форм, поэтому о них
отказывает объявление, а не документ.

`document` и `served` бросают на негодном аргументе — роутере без
`routes`, документе не таблицей, незнакомой настройке — тоже строкой
вызывающего: «роутер.routes — функция или вызываемая таблица, а не nil».
Путь документа, записанный не таблицей, — сломанный документ, а не
расхождение с кодом, и `served` о нём бросает: «документ.paths[/b] —
таблица, а не box.NULL».

## Чем пришлось поступиться

- **Слова пишутся рядом с объявлением, а не в нём.** Описание операции —
  отдельная таблица по имени маршрута, а не поле маршрута: роутер не знает
  об описании, и пакет, которому описание не нужно, его не тянет.
  Цена — имя пишется дважды; сверка ловит опечатку в нём расхождением.
- **Только OpenAPI 3.0.** Схемы форм написаны по 3.0 (`nullable`,
  `writeOnly`), а в 3.1 `nullable` уже нет.
- **Проверка параметра, которой нет в шаблоне, не видна.** Своя проверка
  функцией и ограничение группы `where` описываются строкой: по
  объявленному маршруту их не видно.
- **Короткие пути без опознавателя.** Путь без необязательного участка —
  тот же маршрут, а `operationId` в документе единственный.
- **`ANY` не описывается.** Маршрут на любой способ — расхождение: какие
  способы у него есть на самом деле, знает только обработчик.
- **Начало путей — у первого сервера.** Остальные серверы — те же точки
  входа по другим адресам; сервер с другим путём в том же документе
  описать нельзя.
- **Ответ и тело не выводятся из обработчика.** Что обработчик отдаёт на
  самом деле, по объявлению не видно, и описание ответа — слово того,
  кто пишет операцию. Согласие схемы с формой держит то, что схема и есть
  форма, а у списка — что схему ответа выводит тот же запрос, который
  этот ответ собирает.
- **Порядок ключей в YAML не постоянный.** Встроенный `yaml.encode` ключей
  не сортирует; файл, собранный заново, сверяют с прежним таблицами
  (`t.assert_equals(yaml.decode(text), Api.document(web))`), а не текстом.
- **Сверка не раскрывает `$ref` у пути.** Путь, описанный ссылкой на чужой
  путь, для `served` без операций.

## Проверки

```sh
make deps          # luatest, luacheck, luacov с cluacov, зависимости пакета и tnt-query в .rocks
make check         # форматирование, линт, проверки, покрытие с порогом 100 %
make mutants-all   # мутационное тестирование утилитой tnt-mutants, порог 100 % убитых
```

Внешней службы у пакета нет, и живых проверок тоже. Проверки лежат
в `test/`, по файлу на возможность: объявление, пути, документ и сверка.
Роутер в них настоящий, а не список маршрутов, написанный руками: иначе
проверки судили бы договор описания с самим собой, а не с тем, что роутер
отдаёт на самом деле. Документ и отказы сличаются целиком и дословно:
документ уходит клиентам API, а отказ — тому, кто объявил описание.
Параметры строки запроса сличаются с настоящим запросом `tnt-query`,
поэтому он стоит в `.rocks` проверок, хотя пакету не нужен. Модули
пакета берутся из исходников, зависимости — установленными. Покрытие
строк — 100 %, убитых мутантов — 100 % (70 проверок; 277 мутантов
в шести модулях).
